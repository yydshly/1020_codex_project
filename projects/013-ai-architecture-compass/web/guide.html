需求决定我们想达到什么；代码保存规则与边界，让后续需求有可靠的落点。每次实现，都需要把目标、结构与实际证据接起来。

01 明确目标

说明用户任务、第一版范围和可观察的成功结果，列出无法接受的失败。

02 确定边界

统一术语，明确业务规则、数据所有者、模块公开入口及允许的依赖。

03 实现与检查

完成一条真实用例，让结构检查与行为验证覆盖关键约束。

04 用证据调整

记录已验证和未验证范围；发生规则重复或改动扩散时，回到模型与边界。

今天的代码也是下一轮 AI 的上下文。你掌握目标与重要取舍，AI 需要提供可审查的实现和证据。

业务建模

领域驱动设计Domain-Driven Design

通过共同语言和领域模型组织业务知识，再划定模型适用的边界。

方法类型
设计方法
关注的问题
业务里的概念、规则与责任，怎样进入代码？
适用场景
业务规则复杂、术语容易混淆、需要长期演化的核心业务。页面多或流量大，本身不足以构成采用理由。
核心原理
战略设计确定核心域、限界上下文及其关系；战术设计用实体、值对象、聚合等表达行为与一致性规则。语言在各自上下文内保持一致。
落地方向
从真实场景和业务规则开始，建立少量核心概念；在一个上下文内实现完整用例，再根据新知识调整模型。
意义
让新需求有明确归属，减少同一概念在不同代码里的相互冲突；便于你审核 AI 是否理解业务。
代价
需要持续澄清业务；简单增删改查可能只需要轻量模型。聚合和上下文都不能直接按数据库表或文件夹机械划分。
何时延后
规则主要是字段校验、概念没有明显冲突时，先统一术语与用例，延后完整的战术模式。
最小动作
选一个有冲突风险的用例，写清术语、规则和一致性范围，并让一个模型承担这些规则。
常见误用
按数据表生成实体、聚合和仓储，却把真正的业务判断继续散落在入口与脚本中。
有效性信号
修改一条业务规则时，能找到明确归属；从不同入口执行同一操作，约束保持一致。
约束示例
正文更新必须检查预期版本；AI 建议记录它所依据的正文版本。规则由内容模型统一维护。
验证证据
场景测试证明旧版本写入会被拒绝；审查所有写入口是否经过规则。静态依赖检查不能证明领域边界正确。
组合关系
可在模块化单体或服务内部采用；通过六边形隔离外部实现，通过用例组织应用层。

代码组织

分层架构Layered Architecture

按技术职责划分展示、业务、数据访问等层，缩小每一部分需要理解的范围。

方法类型
组织方式
关注的问题
界面、业务和数据访问，分别由谁负责？
适用场景
结构相对稳定的信息管理应用，需要先把界面、业务规则和存储职责理清。
核心原理
每层负责一种关注点，调用遵循约定的方向与允许跨越的边界。逻辑分层与部署到几台机器是不同的决策。
落地方向
先划清实际职责，明确允许的调用；通过一条完整流程检验分层是否减少了理解成本。
意义
容易沟通，方便独立理解界面、规则和数据访问，也为验证提供接缝。
代价
一次功能可能要跨多层修改；空转发层、万能 Service 和共享工具堆积会增加理解成本。
何时延后
一个短小流程已经清楚可测时，延后没有独立职责的额外层；不必为每次调用增加转发。
最小动作
从一条保存流程分出输入处理、业务判断和存储访问，标明允许的调用方向。
常见误用
只按 Controller、Service、Repository 命名目录，所有业务都堆进一个万能 Service。
有效性信号
界面调整不牵动业务规则；绕过界面调用业务入口，校验和结果仍然完整。
约束示例
界面通过应用入口发起保存，业务校验不放在按钮事件里；数据访问实现集中维护。
验证证据
检查跨层依赖；绕开 UI 调用保存入口，验证业务规则仍然成立。
组合关系
可在业务模块内部使用，也可与依赖倒置结合；整体按模块划分时不必全仓库共用一个业务层。

垂直切片架构Vertical Slice Architecture

按完整用例组织相关实现，降低不同切片之间的耦合。

方法类型
组织方式
关注的问题
怎样让一次功能改动集中在一个可理解的范围？
适用场景
需求以独立功能持续加入，横向公共层导致每个功能都牵动很多文件。
核心原理
围绕变化的方向聚合代码，例如保存笔记、导出报告各是一条切片；每条切片按自己的复杂度选择实现方式。
落地方向
先按请求或用例归组；共同业务规则出现时提炼到领域模型，简单查询保留直接、清楚的实现。
意义
AI 任务范围更完整，局部改动更容易审查；不同用例可以有不同的实现厚度。
代价
需要识别何时抽取共享规则；切片之间复制核心规则会造成行为漂移。
何时延后
多条流程共用的关键规则尚未明确归属时，先厘清规则所有者，再扩大切片的自主实现范围。
最小动作
把一个完整用例的入口、处理与验证放在一起，保留它依赖的共享业务规则的唯一归属。
常见误用
按每个页面或 API 随意切分，并复制版本校验等共同规则，导致相同操作出现不同结果。
有效性信号
新增或调整用例时改动集中；共享规则改变后，相关切片仍通过同一组业务场景。
约束示例
保存与导出各自拥有应用流程；版本检查等共同业务规则归内容模型统一维护。
验证证据
以用户流程验证切片，审查跨切片依赖和重复规则；不能用改动文件少直接证明架构正确。
组合关系
可放在模块化单体的模块内部；复杂业务使用 DDD，重要外部交互使用端口。

依赖控制

六边形架构Ports & Adapters

业务通过端口表达交互需求，适配器负责接入具体技术。

方法类型
架构模式
关注的问题
怎样让核心业务独立于模型服务、数据库与界面？
适用场景
外部服务变化多，存在多个输入入口，或希望脱离真实外部环境验证核心流程。
核心原理
区分应用内部与外部。输入适配器驱动用例；输出适配器实现业务需要的端口。源码依赖与运行时调用方向需要分别理解。
落地方向
围绕实际业务交互定义小接口；先实现一个真实适配器，在确有需要时加入另一实现或测试替身。
意义
替换模型厂商或存储实现时影响更集中；同一业务可由网页、命令行或任务调度驱动。
代价
为所有函数预设接口会增加负担；接口必须表达业务需要，厂商参数和数据类型需要在边缘转换。
何时延后
某个依赖很稳定，隔离它也不能改善验证或替换成本时，可以延后为它专设端口。
最小动作
挑一个变化频繁的外部接入，按用例需要定义小端口，连接真实适配器并验证失败行为。
常见误用
把厂商 SDK 的参数和返回类型原样搬进端口，形成名义隔离、实际仍受厂商牵动。
有效性信号
外部接入变化主要落在适配器；核心失败场景可独立验证，真实接入也通过契约验证。
约束示例
内容与 AI 用例依赖 TextGenerator 端口；厂商 SDK 仅在接入模块使用。
验证证据
导入检查阻止核心引入 SDK；以真实适配器验证契约，以受控替身验证超时及失败路径。
组合关系
适合 DDD 核心和模块化单体；与整洁、洋葱共享隔离核心的思想，选一套清楚的表达即可。

整洁架构Clean Architecture

围绕业务规则与用例组织系统，要求源码依赖指向内部。

方法类型
架构方法
关注的问题
用例与业务规则怎样免受框架细节牵动？
适用场景
长期维护、入口多、框架与持久化细节可能变化，需要明确业务和应用用例职责。
核心原理
业务实体、应用用例、接口适配和框架细节承担不同职责。外部实现依赖内部约定；跨边界的数据不应绑定外层框架。
落地方向
先明确关键用例和依赖方向，按需要增加边界；示意图中的圈数不等于每个项目必须具有的层数。
意义
让业务规则和用例可以独立理解、测试，降低框架升级对核心的影响。
代价
简单操作也强制穿过许多层，会产生大量转发与对象映射；需要控制接口数量。
何时延后
用例简单、生命周期短，尚无隔离收益时，先保留清楚的依赖方向，延后完整的多圈结构。
最小动作
提取一个关键用例，使它接收独立输入、调用所需契约，再在外层完成框架装配。
常见误用
机械复制架构图中的层数，每层只转发数据；或让 HTTP、ORM 类型越过核心边界。
有效性信号
关键用例可脱离 Web 框架运行；框架接口变化时，业务规则和用例输入无需随之改写。
约束示例
保存用例接收业务输入，不直接接收 HTTP Request 或 ORM 行对象；核心不导入外层实现。
验证证据
包依赖检查、用例测试，以及一次真实存储的集成验证；只检查目录命名不能证明依赖正确。
组合关系
可以承载 DDD 模型；与六边形、洋葱高度重叠，组合时只保留有明确职责的结构。

洋葱架构Onion Architecture

领域模型位于中心，基础设施位于外围，依赖朝向中心。

方法类型
架构模式
关注的问题
怎样围绕领域模型控制长期依赖？
适用场景
领域行为较复杂、长期存续的业务应用，尤其适合已有明确领域模型的系统。
核心原理
核心声明所需行为契约，外围实现持久化、UI 等细节；运行时把实现装配到核心所需接口上。
落地方向
先建立有行为的核心模型，再外置基础设施；将接口放在真正需要它的一侧。
意义
核心模型保持集中，技术实现可以在外围演进。
代价
模型很薄的简单页面可能得不到足够收益；复杂的注入和多重映射需要实际理由。
何时延后
核心只有简单记录读写，尚无值得集中维护的领域行为时，延后围绕领域模型搭建多层结构。
最小动作
选一条重要领域规则移入核心模型，把它需要的存取契约与具体数据库实现分开。
常见误用
把所有接口和工具都放进核心，或让领域对象为了 ORM 的约束承担持久化细节。
有效性信号
领域规则在没有数据库的条件下可验证；持久化实现调整主要局限在外围。
约束示例
领域对象不依赖数据库实现；保存和读取所需的接口由核心一侧定义。
验证证据
验证向外依赖被阻止、领域规则可独立运行，并补充实际存储适配的验证。
组合关系
与 DDD 自然衔接；六边形、整洁、洋葱可以作为同一家族比较，避免重复搭建多套层次。

部署与边界

模块化单体Modular Monolith

内部按业务模块划边界，整体作为一个应用部署。

方法类型
整体结构
关注的问题
怎样让项目变大，同时保持部署和本地运行简单？
适用场景
个人或小团队持续演进产品，需要清楚边界，尚无明确的独立发布、扩容要求。
核心原理
模块封装内部实现，公开有限接口，约定数据所有权与协作关系；单体描述部署方式，模块化描述内部结构。
落地方向
按业务能力划模块，用包或导入规则保护边界；从一个完整用例开始验证，再逐步演进。
意义
减少分布式运行成本，同时让改动、理解和责任更集中。
代价
共享数据库和随意跨模块访问容易侵蚀边界；单纯建几个文件夹不能形成封装。
何时延后
产品只有一两个紧密相关的用例时，先保留少量明确职责，延后大量模块和跨模块协议。
最小动作
找出两个责任不同的业务能力，为各自数据指定所有者，并定义一条公开协作接口。
常见误用
目录按模块划分，运行时却任意写对方数据，或依赖一个容纳所有业务的 shared 包。
有效性信号
模块内部重构不会迫使其他模块了解实现；完整产品仍能作为一个应用运行和交付。
约束示例
检索模块通过内容模块公开接口获取内容；不直接导入内容内部存储实现。
验证证据
检查模块依赖及数据访问；用完整流程验证协作。真正拆出服务前验证接口及数据所有权。
组合关系
可作为 DDD、切片、六边形的承载结构；满足独立部署条件后再评估特定模块服务化。

微服务架构Microservices

围绕业务能力建立可独立部署的服务，通过明确契约协作。

方法类型
部署结构
关注的问题
哪些业务能力需要独立发布、运行与扩容？
适用场景
独立扩容、发布节奏、团队自治或运行隔离已有明确需求，并具备相应运行维护能力。
核心原理
服务拥有自己的责任和数据，通过远程接口或消息协作；网络、超时和局部失败成为正常设计条件。
落地方向
先确认业务边界及拆分收益，优先评估一个压力明确的模块，再建立契约、观测与故障处理。
意义
特定能力可以独立发布和扩展，允许不同部分采用适合的运行方式。
代价
增加通信、数据一致性、部署、调试和监控成本；服务互相牵制会削弱独立性。
何时延后
独立发布或扩容的收益尚不明确，团队也不能承担分布式运维时，先保持模块化单体。
最小动作
选一个压力可测、数据归属明确的模块，先验证远程契约和独立部署，再决定是否拆出。
常见误用
按技术层拆服务、共用可任意写入的数据库，最终每次改动仍要求所有服务一起发布。
有效性信号
目标能力确实能独立发布或扩容；测得的收益足以覆盖新增通信、故障处理和运维成本。
约束示例
生成服务与内容服务通过版本化契约通信；请求重试可去重，不直接访问对方内部数据。
验证证据
验证契约、超时、重复请求、局部失败和独立部署；根据负载测量确认拆分收益。
组合关系
单个服务内部仍可使用 DDD、六边形或切片；边界稳定也不意味着必须立即拆成服务。

协作与扩展

插件式架构Plug-in / Microkernel

核心提供稳定的扩展点，插件按约定贡献具体能力。

方法类型
扩展方式
关注的问题
怎样持续增加能力，同时控制核心变化？
适用场景
编辑器、工具平台、格式转换、AI 工作台等有反复出现的扩展需求的产品。
核心原理
定义扩展协议、生命周期与依赖约定；宿主负责注册、调用和故障处理，插件负责特定能力。
落地方向
先从两个真实扩展需求提取协议，约定版本兼容和能力范围，再考虑发现、安装和隔离机制。
意义
新增能力可集中实现，核心职责更加稳定，方便独立维护扩展。
代价
协议演进、兼容和故障隔离需要维护；同进程插件本身不提供安全沙箱。
何时延后
目前只有一个固定能力，第二个扩展需求仍是假设时，先用普通模块，延后通用插件协议。
最小动作
用两个真实导出器或处理器验证最小协议，明确输入输出、版本和失败返回。
常见误用
为了未来的任意扩展提前暴露宿主全部内部能力，或把动态加载误当成安全隔离。
有效性信号
新增同类能力主要修改插件；旧插件兼容性与不兼容时的处理均有可重复验证。
约束示例
导出插件只通过宿主提供的内容读取与文件导出能力工作，并声明支持的协议版本。
验证证据
验证插件契约、加载失败与版本不匹配；真正需要安全隔离时另行验证进程或权限边界。
组合关系
宿主可以是模块化单体；内部模块不必都变成可动态加载的插件。
原始定义与说明 ↗
事件驱动架构Event-Driven Architecture

发布已发生的事实，由相关消费者响应并执行后续动作。

方法类型
协作方式
关注的问题
一次变化之后，多个独立动作怎样协作？
适用场景
正文保存后更新索引、发通知、安排分析等可分开执行的后续任务。
核心原理
区分命令与事件，明确事实的发布时间、载荷和所有者；需要可靠交付时设计持久化、重试与去重。
落地方向
先识别允许延后的动作；为重复、乱序、丢失和失败规定行为。仅使用内存事件不等于具备可靠交付。
意义
减轻主流程对后续消费者的直接依赖，方便新增响应者。
代价
整体流程更难从一次调用中看清；需要追踪、失败处理及适当的一致性约定。
何时延后
某组步骤必须立即共同成功或失败时，先保留明确的事务或协调流程，延后异步事件拆分。
最小动作
选一个允许延后的后续动作，定义事实事件与消费者，并写清丢失、重复和失败的处理。
常见误用
把必须完成的命令伪装成事件，或认为发出内存通知就已经解决可靠交付。
有效性信号
新增后续消费者不需改写发布者；失败可追踪和恢复，主流程的一致性约定仍成立。
约束示例
正文持久化后产生内容已更新事件；索引失败可重试，重复消费不会产生重复副作用。
验证证据
覆盖重复、乱序、失败与重启场景；检查提交与事件交付之间的失败窗口。
组合关系
可在单体内局部采用，也可用于服务协作；事件驱动、CQRS、事件溯源可分别选择。

数据与状态

命令查询职责分离CQRS

修改状态和展示查询采用各自需要的模型与处理方式。

方法类型
数据模式
关注的问题
读和写的模型差异明显时，怎样分别设计？
适用场景
写入规则复杂，读取需要搜索、统计或聚合视图，统一模型已经带来明显负担。
核心原理
命令表达要改变什么，查询表达要获取什么；可以先在同一应用、同一数据库内分离，无需立即拆库。
落地方向
只在收益明确的业务部分使用；采用异步读模型时，明确更新延迟和重建方式。
意义
写侧专注规则，读侧按展示需要组织，便于分别优化。
代价
可能增加模型映射、同步和调试成本；普通 CRUD 未必有足够收益。
何时延后
读写使用相近的数据形状且没有明显负担时，保留统一模型，延后读写模型分离。
最小动作
在一个收益明确的业务范围内分开写入用例与查询模型，先共享现有数据库验证价值。
常见误用
仅将函数命名为 Command 和 Query 就声称实现 CQRS，或同时强制拆库、上队列与事件溯源。
有效性信号
复杂查询变化不再扭曲写入规则；读侧数据的新鲜度与维护成本满足已约定的目标。
约束示例
修改正文走版本校验命令；搜索结果采用读取模型，并明确何时反映最新正文。
验证证据
验证写侧规则、查询结果及允许的更新延迟；使用投影时验证重建和失败恢复。
组合关系
可与 DDD、垂直切片及事件驱动结合；不要求微服务或事件溯源。
原始定义与说明 ↗
事件溯源Event Sourcing

保存事件序列，并由事件重建当前或历史状态。

方法类型
状态存储模式
关注的问题
怎样以历史事实作为状态的来源？
适用场景
业务确实需要历史重放、时间点状态和可追溯变更，且这些收益足以承担额外成本。
核心原理
事件序列是状态来源；状态和查询视图由事件计算，可使用快照提高重建效率。普通日志或版本备份并不自动构成事件溯源。
落地方向
先验证重放需求，定义事件语义与演进办法；设计重放时外部副作用的隔离。
意义
可以解释状态怎样形成，按新规则重新计算视图或回看历史。
代价
历史事件兼容、并发追加、快照、隐私处理和副作用重放都需要专门设计。
何时延后
需求只是备份、审计记录或恢复旧版本，普通快照与变更记录已足够时，延后事件溯源。
最小动作
在一个小的业务范围验证事件追加和状态重建，再验证旧事件兼容与重放副作用隔离。
常见误用
给现有状态表追加日志就宣称可重建，或重放历史时再次发送通知、扣费和调用外部服务。
有效性信号
已保存的历史事件可以重建预期状态，版本演进后仍可验证，且重放不会重复外部副作用。
约束示例
同一事件序列重建得到相同状态；重放不得再次发出真实通知或调用收费服务。
验证证据
验证从空状态与快照重放的一致性、历史事件兼容及副作用隔离。
组合关系
可结合 CQRS 构建查询投影，也可独立使用；重要数据需要备份，并不必然要求事件溯源。

采用理由

关键边界
插件协议版本明确；错误可定位；访问数据与文件的能力有范围。
怎样验证

演进条件

假设场景：生成润色建议，由用户决定采纳。AI 用例负责建议，内容模块拥有正文和版本规则。

从规则看边界

  • 生成建议或模型失败，都不修改已保存正文。
  • 建议记录来源版本，采纳时由统一入口原子地维护版本匹配与写入。
  • 模型 SDK 留在适配器，核心用例通过约定端口调用。

用失败场景验收

  • 旧版本建议：无法直接覆盖较新的正文。
  • 同版本并发采纳：实际存储只允许一个请求成功。
  • 模型超时：原文完整，任务有明确失败状态。
  • 保存后重开：读出的内容与已确认结果一致。
  • 索引失败：已保存正文仍可用，索引可以重试。
