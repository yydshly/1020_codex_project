# 历史地图与三维山河接入验收

本次把 016 的完整运行时接入 017 研究网页的独立 iframe。二维历史地图引擎、历史数据与样式来自江山时序；016 新增入口、路线编辑和 Three.js 三维联动；017 新增本地集成入口与控制桥。此接入不等于把历史地形渲染器迁移进深海场景。016 文件保持原样，017 的地图运行时不依赖 8015/8016 服务。

这是一份待执行的验收清单，不把计划当作已通过的浏览器验证。静态文件与依赖验证使用 `node src/check-atlas-integration.mjs`；真实画面、手势与 WebGL 故障恢复仍需浏览器验收。

## 可观察状态与控制边界

- 只有 `body.dataset.workbenchReady === 'true'` 后才允许父页下发业务命令。未就绪应显示加载或失败状态，不吞掉点击，不重复执行旧 iframe 的排队命令。
- 父页使用固定命令白名单；子页只接受同源父窗口消息；父页只接受当前 iframe 的窗口消息。消息含协议版本、请求编号，旧 iframe 的迟到回复不得覆盖新实例状态。禁止消息携带可执行 JavaScript。
- 状态显示至少包含：实际二维/三维模式、年份、人物与站点或自定义路线站点、当前挑战状态、是否播放、是否有 WebGL 上下文中断。年份来自 `app.year`，范围来自 `app.minYear/maxYear`，而非父页维护第二份地图状态。
- 三维运行证据包括可见 canvas、`canvas.dataset.engine`、`frames`/`triangles` 及画面。`ready=true` 单独不能证明上下文健康；上下文中断后必须单独标记故障。
- `atlas-workbench.js` 会重写 URL，丢弃其未认识的参数。嵌入识别必须在首次执行时捕获，或使用 `window.parent !== window`，不能依赖 `embedded=1` 始终留在地址中。

### “恢复视图”的兼容注意

016 在三维模式下 `app.resetCamera()` 只重置三维镜头；二维源引擎的 `resetCamera()` 会先清除自定义路线。如果 017 的“恢复视图”承诺仅恢复镜头，则二维桥应使用 `app._animateCameraTo(app._getDefaultCamera())`，或先完整保存并恢复路线；不能直接调用原二维 reset 导致已生成路线消失。人物“全图总览”和自定义路线“全线视图”另有各自功能，不应混为同一个含糊命令。

## 生命周期与故障恢复

1. **仅一个地图实例。** 重复点击“打开地图”不创建第二个 iframe，不累加 `message` 监听器。页面只有一个当前实例代号，过期状态被忽略。
2. **离开可见区暂停播放。** 调用 `app.stopAutoplay()` 可同时停止年份播放与人物播放。它不停止 Three.js RAF；若采用切到二维暂停三维渲染，必须记住用户先前模式，返回时恢复。不可仅隐藏 iframe 就声称已暂停渲染。iframe 完全卸载可终止其循环，但要先保存足以恢复的状态与草稿。
3. **保留手工状态。** 暂停不能重建 iframe。显式关闭/重启前保存当前 iframe URL、二维镜头（若承诺恢复）、路线对话框输入与是否打开、当前视图；没有 URL 编码的图层配置也需另存。重新载入后等待就绪，再恢复草稿与配置，最后恢复用户所选模式。
4. **上下文中断的最小修复。** 016 的 `webglcontextlost` 回调会隐藏三维 host，但 workbench 模式仍显示三维，造成空白。切换二维再切三维可能把 `ready` 重新置 true，却不保证 GPU 恢复。017 桥监听一次 context-lost 后明确回报“已中断”，自动降为可用二维并给出“重启三维地图”动作；显式重启时用当前状态新建 iframe。不要自动无限 reload，也不要仅把 `ready=true` 当成修复。新实例才清除旧 context-lost 标记。
5. **重启可验收。** 在三维秦统一第三站触发测试用上下文中断后，父页状态有说明、二维能用；点击重启一次，只产生一个新实例；人物、站点、年份、层配置与路线草稿按约定恢复；没有黑/白屏冒充成功。
6. **故障有出口。** 首次加载失败、3D import/DEM 失败、超时、上下文中断分别显示原因与重试入口。重试由用户显式触发，监听器/定时器销毁，不重复提交上一命令。
