# 004 · 数字人技术图谱

我们要研究的是：**如何在租用 GPU、控制持续运行成本的前提下，做出外观可信、动作自然、能实时对话的数字人，并保留后续替换模型和扩展产品的空间。** 这份可交互中文网页从我们已有的「角色图片 → 动作素材 → MuseTalk 实时口型」系统出发，比较八条技术路线的生成机制、落地流程、代表库、效果边界、硬件与许可。资料核对日期：**2026-10-23**。

**当前最适合我们的主线是：优质动作素材 + MuseTalk 实时口型 + 状态与情绪编排，保留 Ditto 回退；把 FlashHead Lite 作为单独的实验后端。** 这是基于已有系统、成本目标和工程可控性的选型判断，不是统一测试得出的画质冠军。

## 研究问题与结论

“真实感”需要分别评估：外观是否可信、口型是否同步、头部和身体动作是否自然、反应是否及时、长时间使用是否重复。图片决定角色身份，动作素材或运动模型决定身体与表情如何变化，口型模型主要负责发音匹配；对话、语音、切换与打断机制共同决定交互体验。

因此，本研究不是寻找一个包办所有效果的模型，而是回答：哪些能力可以由现有素材稳定提供，哪些能力值得增加实时推理成本，以及何时需要转向可精确控制的三维角色。

| 决策 | 当前判断 | 适用条件与下一步 |
| --- | --- | --- |
| 最适合当前项目 | 优质动作素材 + MuseTalk，Ditto 回退 | 复用已经搭建的服务，先优化素材质量、情绪协调、切换、音画同步和打断；再用固定测试集测时延、稳定性与有效会话成本。 |
| 减少素材依赖的实验 | FlashHead Lite 等单图驱动后端 | 与主线使用同一角色、音频和测试场景；通过实测判断动作自然度、口型、重复感和资源占用是否值得替换。 |
| 追求生成式复杂动作与视觉表现 | 以 Vidu 等流式生成方案作效果参照 | 需单独验证长时身份稳定、动作可控、时延、费用与服务限制；不能直接认定它在所有指标上“效果最好”。 |
| 追求空间控制与明确身体动作 | 高质量 3D 角色 + 面部驱动 + 身体动画 / IK | 适合需要转身、走动、指物和物体互动的产品；角色资产、绑定、动画与渲染决定最终观感，单独接入口型模型不够。 |

## 八条路线如何落地

| 技术路线 | 落地方式与代表库 | 主要优势 | 主要限制 |
| --- | --- | --- | --- |
| 素材视频 + 口型重绘 | 录制或生成动作片段 → 预处理 → 按状态选片 → MuseTalk 重绘口部；可比较 Wav2Lip、LatentSync，RIFE 用于有限条件下的过渡 | 身体动作和光影继承素材，视觉可控；可复用预处理和已有服务 | 动作范围受素材限制，循环和切换可能露馅；口型模型不会自动生成任意身体行为。原版 Wav2Lip 有非商业限制；不同模型不都适合实时运行。 |
| 单图 + 运动驱动 | 角色图 → 音频或运动条件 → Ditto、LivePortrait、SadTalker、SoulX-FlashHead 等 → 视频帧 | 创建角色门槛低，可减少固定视频素材依赖 | 各模型驱动条件不同；转头、遮挡、牙齿、手部和长时稳定性需验证，不能把所有单图模型当作同一种能力。 |
| 离线生成式说话视频 | 角色图、音频及可选姿态 → EchoMimicV2、Hallo 等 → 完整视频 → 作为内容或素材入库 | 适合预制表演、丰富动作库，可把较重计算移出实时链路 | 生成等待、角色一致性和可控性有边界；离线高质量不代表适合即时聊天。 |
| 流式生成视频 | 持续音频 / 条件 → FlashTalk、LiveAvatar 或 Vidu 等 → 连续视频块 → 同步播放 | 有机会生成随内容变化的表情和动作，减少机械循环 | 实时性高度依赖具体硬件、配置与服务；重模型成本、长时漂移和队列时延需实测，商业服务不等于开源可部署。 |
| 显式 3D 角色 | GLB / VRM / MetaHuman 等角色资产 → Audio2Face、视素或面部捕捉 → 身体动画与 IK → Three.js / 引擎渲染；可用 TalkingHead、three-vrm、Rhubarb | 视角、骨骼、空间位置和物体互动更可控，可形成可复用角色资产 | 写实程度取决于建模、绑定、材质、动画和渲染；面部驱动只是其中一环，接入与制作投入较大。 |
| NeRF / 3DGS 神经渲染 | 采集特定人物视频 → 训练个人表示 → 音频 / 姿态驱动 → RAD-NeRF、ER-NeRF、GeneFace++、TalkingGaussian 等渲染 | 在训练覆盖范围内可保留人物外观与连续感 | 通常需要人物数据和训练；视角、姿态、换装及新身份的泛化受限，不等同于可自由编辑的通用 3D 模型。 |
| Live2D / 2D 木偶 | 分层原画 → 参数与变形绑定 → 音量 / 视素 / 表情状态 → Live2D 等渲染 | 适合风格化角色；动作与表情可以明确设计，交互运行负担通常较轻 | 表现空间由原画和绑定决定；不直接提供写真人像效果，Live2D 的 SDK 与素材许可需分别确认。 |
| 实时视频编辑 | 已有驱动视频 → Vidu S2 等编辑能力 → 改变人物或场景 → 输出视频 | 可以沿用输入视频的动作组织，探索换角色、换场景等玩法 | 依赖持续输入视频；身份、背景、服饰与时间一致性及延迟都需验证，不等同于从零自主生成动作。 |

以上是机制层面的比较。库名称是代表入口；具体输入、硬件和许可见网页详情与模型目录，不能跨硬件直接比较官方 FPS。

## 研究的意义

- **把模型能力与系统编排分开。** 角色生成、动作、口型、语音、对话和视频播放分别承担职责，避免把一个产品演示的全部效果归功于某个模型。
- **把效果、成本与可控性拆开评估。** 看起来最惊艳的片段未必适合长时间互动；有效会话成本还包含启动、空闲、失败重试、语音和服务费用。
- **形成可以复用的实验标准。** 固定角色、音频、情绪和打断场景，记录口型、动作、时延、身份稳定与长时运行结果，再决定是否切换后端。
- **保留迭代空间。** 统一角色素材、状态、语音时间轴和渲染接口，使素材口型、单图驱动、3D 与流式生成可以逐步验证和替换。

## 可扩展的产品方向

| 产品方向 | 适合从哪里起步 | 需要继续补齐的能力 |
| --- | --- | --- |
| 角色陪伴与情绪互动 | 素材 + 口型或单图驱动，建立稳定角色形象 | 记忆、用户可控的角色设定、情绪与语音协调、自然打断和长时动作变化。 |
| 客服、展厅与业务导览 | 素材 + 口型，按业务状态编排 | 知识检索、工具调用、可核验回答、转人工与服务状态；需要指物和空间引导时引入 3D。 |
| 教学、语言练习与情景训练 | 素材 + 口型用于讲解，3D 用于动作或空间示范 | 课程与任务设计、可追溯评估、学习进度，以及多角色对练。 |
| 虚拟直播与内容呈现 | 动作素材库 + 实时口型，或风格化 3D / Live2D | 消息筛选、队列、观众互动、场景切换、OBS 输出和长时稳定；可用离线生成补充表演片段。 |
| 角色素材与生产工具 | 图片到动作素材、预处理与标签管理 | 角色一致性检查、片段质量检查、循环与过渡预览、版本管理和批量生产。 |
| 可插拔数字人服务 | 统一对话、语音、状态与渲染接口 | 后端路由、监控、成本统计、降级、队列与会话隔离，按质量与预算选用不同模型。 |

这些是基于技术能力提出的产品扩展方向，不是已实现功能或市场验证结论。

## 内容范围

共 8 条路线、31 个代表模型与工具、33 个来源入口，分成 13 个阅读章节：

1. 共同理解：分别看外观真实、动作自由、互动自然和运行成本。
2. 八条路线：素材视频配口型、单图运动驱动、离线生成、流式生成、显式 3D、NeRF / 3DGS、Live2D、视频实时编辑。
3. 我们的系统：MuseTalk、Ditto、动作片段库、RIFE、MiniMax、SenseVoice 和网页服务之间的关系。
4. 能力矩阵：外观、控制、动作、长时体验、运行支出与开发投入。
5. 模型目录：搜索、按路线与部署方式筛选、详情来源、最多四项并排对比。
6. 原理拆解：MuseTalk 的局部重绘、3D 角色的面部与身体驱动、Vidu 的流式视频生成。
7. 素材与情绪工程：录制和 AI 底片、循环与切换、情绪协调、素材字段示例。
8. 租卡成本：卡数、准备时间、并发、利用率、固定费用和语音费用可编辑估算。
9. 试验记录：10 项检查清单、本地保存、导出含空白实测字段的 JSON 模板。
10. 演进选择：按低成本聊天、减少重复、复杂动作、空间控制、风格化角色给出下一步实验。
11. 产品方向：陪伴、客服导览、口语教学、虚拟直播、素材管理与可插拔服务，说明最小落地与验证入口。
12. 术语速查：口型、视素、绑定、IK、NeRF、3DGS、时延与音画同步等。
13. 证据来源：原始文档、仓库版本与已知限制。

## 本地运行

需要 Node.js 18+ 和 Python 3.10+，无需 npm 安装依赖。在本目录运行：

```powershell
npm run build
npm run check
npm run preview
```

浏览器打开 `http://127.0.0.1:8044/`。端口冲突时可运行 `python src/serve.py --port 8045`。预览服务仅监听本机；终端 Ctrl+C 停止。

页面不依赖外部字体、CDN 或后端。清单进度保存在浏览器本地；直接打开文件时，部分浏览器可能限制本地存储，页面会降级为本次临时状态。

## 证据与限制

- 26 个仓库记录了 commit 和 README 哈希；这是资料读取证据，不是模型运行结果。
- 网页的能力比较是带条件的机制分析，没有虚构画质分数、统一测试成绩或可保证的租卡配置。
- Vidu 原帖费用是作者历史案例，未当作现价；计算器默认数值只是可编辑示例。
- 旧 Vidu 文档入口本次不可用，相关原理依据更新为官方产品介绍和公开论文。
- 当前用户系统未提供源代码、输出录像与性能日志，架构图不代表对实际实现的审计。
- 并发按整套部署的成功会话数计算，增加 GPU 数只增加租费，不自动线性增加并发能力。

本项目已接入仓库项目目录，`web: true` 表示静态产物已准备好。本次计划提交到远端并通过 GitHub Pages 发布到上方在线地址；提交、部署状态与在线可达性需由发布流程分别确认。根仓库可以使用 `python scripts/projects.py check` 与 `python scripts/projects.py build` 验证并生成站点。

页面文本为资料整理与工程分析，封面和流程图为自制示意；模型、权重和第三方素材仍适用各自许可。
